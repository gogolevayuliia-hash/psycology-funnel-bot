## Почему часть проверок физически возможна только ПОСЛЕ merge

Выкат на CT 110 (`deploy.sh`) делает `git -C repo pull --ff-only` из `origin/main` —
другого способа доставить код на контейнер нет. Поэтому сквозной путь
Telegram → Cloudflare Edge → тоннель CT 103 → uvicorn на CT 110 до merge не проверить.
Это признаётся прямо, а не выдаётся за проверенное.

## Что круги критики поменяли по существу

**Круг 1** снёс мою же выдумку: дедупликацию `update_id` через общий Redis. Она лечила риск,
которого в этой схеме почти нет (200 отдаётся до обработки, Telegram не переспрашивает), и
вносила два критических отказа — молчаливую потерю всех апдейтов при любой ошибке Upstash и
возможность заглушить бота на сутки, заняв диапазон id через публичный `/webhook`.

**Круг 2** поймал три регрессии в моих же исправлениях круга 1: `compare_digest` на строках
падал `TypeError` на кириллице в заголовке (500 вместо 403 на публичном эндпоинте), снятие
падения lifespan убрало неявный повтор через рестарт контейнера (моргнувшая сеть = немой бот
навсегда), а защита статистики не покрывала `seed_historical_sales`. Плюс нашёл, что
пересозданный в фазе 0 контейнер **прямо в тот момент портил боевую статистику** — старый код
без защиты каждые 5 минут перезаписывал общий снимок замороженными значениями. Контейнер
погашен до выката, порча остановлена.

## Осторожно при чтении цифр дашборда

1. Smoke-прогон пойдёт по **боевому** боту с тест-аккаунта `@stickers_support`: он накрутит
   счётчики воронки и создаст лид тест-юзера в Notion. Снимок «до» — в `preflight.md`.
2. Пока копия на Railway жива, снимок статистики в общем Redis пишут обе копии по очереди.
   После выката CT 110 станет активной (с `PUBLIC_URL`), а Railway — припаркованной, и с новым
   кодом припаркованная в Redis не пишет вообще. До выката CT 110 держим **погашенным**.
