# WEB: Как безопасно переключить вебхук Telegram-бота на новый URL без потери апдейтов

## Ответ
Заранее запустите новый endpoint, затем вызовите `setWebhook` сразу с новым URL и `drop_pending_updates=false`; `deleteWebhook` перед этим не нужен. Очередь сохраняется и направляется новому вебхуку, а удаляется только при явном `drop_pending_updates=true`; старые апдейты хранятся Telegram не более 24 часов. После успешного ответа проверьте конфигурацию через `getWebhookInfo`, отправьте тестовый апдейт и убедитесь, что он пришёл с правильным `secret_token`. Обработчик должен быть идемпотентным по `update_id`, а старый endpoint разумно временно оставить доступным из-за отсутствия документированной гарантии насчёт запросов, уже находящихся в полёте.

## Факты и источники
- `setWebhook` можно вызвать непосредственно с новым HTTPS URL; метод возвращает `True` при успехе. `deleteWebhook` предназначен для удаления интеграции, в частности при переходе к `getUpdates`, а не как обязательный этап смены адреса — https://core.telegram.org/bots/api#setwebhook и https://core.telegram.org/bots/api#deletewebhook
- Официальная реализация Bot API при смене URL сначала закрывает старый webhook actor, затем устанавливает новый; очередь очищается только если `drop_pending_updates` истинно — https://github.com/tdlib/telegram-bot-api/blob/master/telegram-bot-api/Client.cpp#L15673-L15740 и https://github.com/tdlib/telegram-bot-api/blob/master/telegram-bot-api/Client.cpp#L15926-L15933
- Входящие апдейты хранятся на сервере до доставки, но не дольше 24 часов. `update_id` предназначен в том числе для игнорирования повторов и восстановления порядка — https://core.telegram.org/bots/api#getting-updates
- `drop_pending_updates=true` безвозвратно отбрасывает все ожидающие апдейты. Для миграции без потерь его следует оставить `false` или не передавать — https://core.telegram.org/bots/api#setwebhook
- `secret_token` передаётся в каждом запросе в заголовке `X-Telegram-Bot-Api-Secret-Token`; допустимы 1–256 символов из `A-Z`, `a-z`, `0-9`, `_`, `-` — https://core.telegram.org/bots/api#setwebhook
- `max_connections` ограничивает число параллельных HTTPS-соединений: 1–100, по умолчанию 40. Его выбирают по способности нового endpoint обрабатывать параллельную нагрузку — https://core.telegram.org/bots/api#setwebhook
- Если `allowed_updates` не передан, сохраняется предыдущее значение. Фильтр не действует задним числом на уже созданные апдейты, поэтому при миграции лучше передать список явно и быть готовым принять старые типы из очереди — https://core.telegram.org/bots/api#setwebhook
- `getWebhookInfo` показывает текущий `url`, фактически используемый `ip_address`, `pending_update_count`, `max_connections`, `allowed_updates`, а также `last_error_date`, `last_error_message` и ошибку синхронизации — https://core.telegram.org/bots/api#getwebhookinfo
- Значение `secret_token` через `getWebhookInfo` не возвращается; проверить его можно только по заголовку реального тестового webhook-запроса — https://core.telegram.org/bots/api#webhookinfo
- Telegram повторяет доставку, если endpoint ответил кодом вне диапазона `2xx`. Поэтому новый обработчик должен отвечать `2xx` только после надёжного принятия апдейта в обработку — https://core.telegram.org/bots/api#setwebhook

## Осторожно
- Документация не даёт строгой гарантии о судьбе HTTP-запросов, уже отправленных старому URL в момент переключения. Возможные повторы следует нейтрализовать идемпотентностью по `update_id`, а старый endpoint — не выключать мгновенно.
- Успешный `setWebhook` подтверждает принятие конфигурации, но не доказывает успешную прикладную обработку новым endpoint. Нужны `getWebhookInfo` и реальный тестовый апдейт.
- Изменение `allowed_updates` во время миграции может выглядеть как пропуск или появление «лишних» событий, поскольку фильтр не применяется к уже созданным апдейтам.

## Не нашёл
- Официально установленного grace period, после которого гарантированно можно отключить старый endpoint.
- Документированной гарантии строго однократной доставки при смене URL.
